Layer 2 · Network layer
Network layer & IPv4
Sends IP datagrams from a source network to the destination network
Performs host addressing and packet routing
IPv4 · 32-bit addresses → 232 total
one byte = eight bits · 4 bytes × 8 = 32 bits
Addresses got exhausted in 2011
Guaranteed delivery & data integrity handled by upper layers, e.g. TCP
Formally described in RFC 791
Layer 2 · Network layer

128 bits → 2128 addresses
≈ 3.4 × 1038 = 340,282,366,920,938,463,374,607,432,768,211,456

example address (illustrative)

Layer 3 · Transport layer
Transport layer & TCP
End-to-end message transfer, independent of the underlying network
TCP — Transmission Control Protocol
Connection-oriented and stateful
Reliable transmission · error detection · flow control · congestion control
Most widely used; reliable, in-order delivery of packets
Avoids network congestion and congestion collapse
Layer 3 · Transport layer
UDP — User Datagram Protocol
Connectionless and stateless
Asynchronous protocol
For time-sensitive applications
Transaction-oriented, stateless
No guaranteed delivery
Comparison
TCP vs UDP
TCP
Slower but reliable transfers
Typical: email, web browsing
UDP
Fast but non-guaranteed ("best effort")
Typical: VoIP, music streaming
Layer 4 · Application layer
Application layer & HTTP
Defines how applications interface with lower layer protocols to send data over a network
HTTP — Hypertext Transfer Protocol
Foundation of the World Wide Web
Request–response model
Stateless protocol
Uses URIs (Universal Resource Identifiers)
IoT application protocols · 1
CoAP — Constrained Application Protocol
Freely available, usable for any IoT device
Designed for the needs of HTTP-based IoT systems
Relies on UDP for establishing secure communication between endpoints
Quality of Service (with acknowledgement messages)
Extremely light — for battery-operated / low-energy devices
Good match for web service-based IoT systems
IoT application protocols · 2
MQTT — Message Queuing Telemetry Transport
Widely adopted in the Industrial IoT (IIoT)
Simple, lightweight publish/subscribe messaging
Designed for battery-powered devices
Publisher · Broker · Subscriber model
Features
Minimum bandwidth use; wireless networks
Low energy consumption · good reliability
Little processing and memory resources
IoT application protocols · 3
XMPP — Extensible Messaging & Presence Protocol
Developed by the open source community
For message-oriented middleware, based on the XML language
Real-time exchange of structured but extensible data between two or more network clients
<message to="sensor@iot"><temp>32</temp></message>
Drawbacks
No Quality of Service
No end-to-end encryption
IoT application protocols · 4
DDS — Data-Distribution Service
Falls under the publish-subscribe methodology
Designed by the Object Management Group (OMG)
For real-time M2M communication; enables:
scalablereliablehigh-performanceinteroperable
data exchange between connected devices
independent of the hardware and the software platform
IoT application protocols · 4
Applications of DDS (IIoT)
air-traffic control
smart grid management
autonomous vehicles
transportation systems
robotics
power generation
healthcare services
Overall: DDS manages data exchange between lightweight devices, and interconnects large, high-performance sensor networks.
IoT application protocols · 5
AMQP — Advanced Message Queuing Protocol
Open standard publish/subscribe type protocol
Roots in the financial services sector
Features
message orientation queuing routing: point-to-point + publish-and-subscribe reliability security
Can guarantee complete transactions
Limitation
Due to its heaviness, AMQP is not suitable for sensor devices with limited:
memory
power
network bandwidth
Exam recap
Remember these
Models: OSI 7 · TCP/IP 5 · IoT stack 4 (link, network, transport, application)
Link: Ethernet, Wi-Fi, WiMax, LR-WPAN, 2G/3G/4G · Net: IPv4 32b, IPv6 128b, 6LoWPAN
TCP reliable, connection-oriented · UDP fast, connectionless, best effort
CoAP light, UDP, web-style · MQTT pub/sub + broker, IIoT
XMPP XML, no QoS, no E2E encryption · DDS pub/sub by OMG, real-time
AMQP pub/sub, finance roots, complete transactions, too heavy for sensors
