Communication model 1
Request–Response model
Client sends requests; server responds to the requests
On a request, the server decides how to respond,
fetches the data, retrieves resource representations, prepares the response,
and then sends the response to the client
Communication model 2
Publish–Subscribe model
Publishers · Brokers · Consumers
Publishers are the source of data
Publishers send data to topics, managed by the broker
Publishers are not aware of the consumers
Consumers subscribe to topics managed by the broker
Broker receives data for a topic → sends it to all subscribed consumers
Communication model 2
Publish–Subscribe with topics
Communication model 3
Push–Pull model
Producers push data to queues; consumers pull data from the queues
Producers do not need to be aware of the consumers
Queues help in decoupling the messaging between producers and consumers
Queues act as a buffer when push rate ≠ pull rate
Communication model 4
Exclusive Pair model
Bidirectional, fully duplex
Uses a persistent connection between client and server
Once set up, stays open until the client requests to close
Client and server can send messages to each other after connection setup

REST-based communication APIs

Focuses on a system's resources, and how resource states are addressed and transferred
REST APIs follow the request–response communication model
Constraints apply to the components, connectors and data elements, within a distributed hypermedia system

Communication APIs
REST constraints
1 · Client–server
Client and server separated; each can evolve independently
2 · Stateless
Each request carries all info; server stores no client state
3 · Cache-able
Responses marked cacheable or not, to improve performance
4 · Layered system
Client can't tell if it reaches the server or an intermediary
5 · Uniform interface
Resources identified by URIs, manipulated the same standard way
6 · Code on demand
Server may send executable code — the only optional one

IoT system components
Device · Resource · Controller Service
Device: allows identification, remote sensing and remote monitoring capabilities
Resource: software components on the IoT device for
accessing, processing & storing sensor info controlling actuators enabling network access
Controller Service: a native service that runs on the device and interacts with the web services
Sends data device → web service; receives commands from the application (via web services) to control the device
IoT system components
Database · Web Service · Analysis · Application
Database
Local or in the cloud; stores the data generated by the IoT device
Web Service
Link between IoT device, application, database & analysis
HTTP + REST → REST service · WebSocket protocol → WebSocket service
Analysis Component
Analyzes IoT data; generates results in a form easy for the user to understand
Application
Interface to control and monitor the IoT system
Also to view system status and processed data

IoT levels
IoT Level-1
Single node/device: sensing and/or actuation, stores data, performs analysis, hosts the application
Everything is local
For low-cost, low-complexity solutions; data not big; analysis not computationally intensive
Example: Home automation system
lighting control · smoke detector · mailbox sensor · doorbell · intrusion detector · electric pot · AC control · sprinkler
IoT levels
IoT Level-2
Single node: sensing and/or actuation and local analysis
Data stored in the cloud; application usually cloud-based
Data involved is big, but primary analysis is not computationally intensive → done locally
Example: Smart irrigation
temperature · moisture · pressure · health · connectivity
IoT levels
IoT Level-3
Single node; data stored and analyzed in the cloud; app cloud-based
Data big and analysis computationally intensive
Example: Tracking package handling
Accelerometer: senses movement / vibrations
Gyroscope: gives orientation info
WebSocket service — sensor data sent in real time
IoT levels
IoT Level-4
Multiple nodes with local analysis; data in the cloud; app cloud-based
Local & cloud-based observer nodes subscribe to / receive info collected in the cloud
Multiple nodes needed, data big, analysis computationally intensive
Example: Noise monitoring
sound sensors at many locations
IoT levels
IoT Level-5
Multiple end nodes + one coordinator node
End nodes: sensing and/or actuation
Coordinator collects from end nodes, sends to cloud
Stored & analyzed in cloud; app cloud-based
For wireless sensor networks; big data; intensive analysis
Example: Forest fire detection — detect early, while controllable
temperature · smoke · weather · slope of the earth · wind speed · speed of fire spread · flame length
IoT levels
IoT Level-6
Multiple independent end nodes sense/act and send data to the cloud
Data in cloud; app cloud-based
Analytics component analyzes, stores results in cloud database
Results visualized with the cloud app
Centralized controller: knows status of all end nodes, sends control commands
Example: Weather monitoring system
wind speed & direction · solar radiation · temperature (air, water, soil) · relative humidity · precipitation · snow depth · barometric pressure · soil moisture

Exam recap
Remember these
Req–Res: client asks, server answers · Pub–Sub: publisher → broker topics → subscribers
Push–Pull: producers push to queues, consumers pull · queues decouple + buffer
Exclusive pair: bidirectional, full duplex, persistent connection
REST → request–response, 6 constraints · WebSocket → exclusive pair
